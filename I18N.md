# i18n & SEO pipeline (ARY-401, full-locale machine translation ARY-427)

How the marketing site does **crawlable, localized, SEO-correct pages**. Every
Phase-1 page is published in the **full set of locales the Vaulto app supports**
(16: en, es, fr, pt, de, it, nl, zh, ja, ar, hi, ru, pl, tr, ko, sv — enumerated
to match the app's i18n catalog). English is the canonical source; every other
locale is a **$0 machine translation** generated via the OpenAI API by a
committed, repeatable script (board directive ARY-425).

## Architecture (content-only localization)

- **English source of truth** lives as JSON under `src/i18n/content/<group>/en.json`,
  one group per surface: `chrome` (nav/footer/CTAs), `home`, `how-it-works`,
  `features`, `planning`, `security`, `privacy`, `faq`. Only translatable *text*
  is in JSON — emoji/icons, URLs, hrefs, and email links stay in the components.
- **Translations** are sibling files `src/i18n/content/<group>/<locale>.json`,
  generated by `scripts/translate.mjs`. `getContent(group, locale)` deep-merges
  the locale overlay over English, so any missing/blank string falls back to
  English — a partially-translated locale never ships a hole.
- **One page component per page** (`src/components/pages/<Name>Page.astro`, plus
  `HomePage.astro`) takes a `locale` prop and renders from `getContent`.
- **Routing**: the English page is un-prefixed at `src/pages/<page>.astro`; a
  single dynamic route `src/pages/[locale]/<page>.astro` (`getStaticPaths` over
  `NON_DEFAULT_LOCALES`) emits every other locale (`/fr/security/`, `/ja/faq/`, …).
  Arabic gets `<html dir="rtl">` automatically (`dirFor` in `config/i18n.ts`).

## Re-translating after an English copy change ($0, repeatable)

1. Edit the English JSON (`src/i18n/content/<group>/en.json`).
2. Pull the OpenAI key at run time (never commit it) and run the script:
   ```sh
   # key lives on the Render API service env (AI_INTEGRATIONS_OPENAI_API_KEY);
   # export OPENAI_API_KEY / OPENAI_BASE_URL, then:
   node scripts/translate.mjs --group=<group> --force   # re-translate one group
   node scripts/translate.mjs                            # fill only missing files
   ```
   The script preserves brand "Vaulto", HTML tags, emoji, placeholders, and the
   security/legal claim semantics (glossary + guardrails baked into the prompt),
   and structurally validates each result before writing.
3. `npm run build`. hreflang, self-canonicals, `<html lang/dir>`, and the
   localized sitemap (`xhtml:link` alternates) all update automatically.

## Locale register & variant (pt) — brand lexicon

Some languages have variants or an address register that "translate it naturally"
does not pin down. Left unstated, each re-run of `translate.mjs` re-rolls the
choice **per group**, so one page ends up in one variant and the next page in
another. That is what happened to `pt`: `/privacy` shipped European Portuguese
(`ficheiros`, `palavras-passe`, tu-form) while `/security` shipped Brazilian
Portuguese (`arquivos`, `senhas`, `criptografia`) — on the two pages whose whole
job is to look trustworthy (ARY-1433).

**Ruling (ARY-4507, supersedes ARY-1433) — `pt` is one locale, one variant:
Brazilian Portuguese (pt-BR).** `/pt/` declares `lang="pt-BR"` and
`hreflang="pt-BR"` via `HREFLANG` in `src/config/i18n.ts`; the route stays `/pt/`.
There is no `pt-PT`. Serving Portugal would need its own currency, legal and
estate-planning framing, so it must be a deliberate new locale, never per-file drift.

### Why this flipped (read before flipping it back)

ARY-1433 originally ruled **pt-PT** on three premises. ARY-4507 re-measured each
one rather than re-arguing the conclusion:

1. ~~"It agrees with the app."~~ — **still true, and now the app is the side that
   is wrong.** `lib/i18n`'s `pt` block measures 67 pt-PT lexicon markers against
   14 pt-BR (`ficheiro`, `gerir`, `utilizador`, `registar`, `A eliminar…`,
   `comprovativos`). Marketing is no longer allowed to wait for it: the board
   directive names the market, and a site that matches a wrong app is still wrong.
   Realigning the app's `pt` catalog is tracked separately — and it is the bigger
   exposure, because the app is what a user actually lives in.
2. ~~"It agrees with most of the site already."~~ — this was always a statement
   about the **cost** of changing, not about which variant is **right**. Cost is
   not a tiebreaker once the audience is settled; it is just work (≈9,000 words,
   14 surfaces, done in one pass).
3. ~~"It matches who we sell to … Portugal and Portuguese speakers in the UK/EU
   are the realistic `pt` audience today."~~ — **falsified.** Board directive
   **ARY-4458** (2026-11-09) narrows v1 to **Brazil and the United Kingdom**, with
   **pt-BR and en-GB** as the shipped languages. Premise 3 was the only one that
   spoke to the audience, so the ruling follows the audience.

The failure mode ARY-1433 was created to stop — `translate.mjs` re-rolling the
variant per group, so `/privacy` and `/security` disagree — is **unchanged and
still guarded**. Only the target variant moved.

**Address register: formal-polite `você` + third person.** `você` plus
third-person-singular verbs is the standard Brazilian business register — "Comece
grátis", "Saiba o que você tem", "seus dados". Never the `tu` forms (`o teu cofre`,
`podes`, `vês`). Note the deliberate reversal from the ARY-1433 contract: `você`
**is** the correct subject pronoun here and must *not* be suppressed the way pt-PT
suppresses it. Possessives normally drop the article (`seus dados`, not `os seus
dados`), the progressive takes the gerund (`está guardando`, never `está a
guardar`), and `em outro` is written out rather than contracted to `noutro`.
`src/i18n/content/home/pt.json` is the reference implementation.

**Required lexicon** — use the pt-BR term, never the European one:

|---|---|---|
| computer file | arquivo | ficheiro |
| password | senha | palavra-passe |

| screen | tela | ecrã |

\* `Configurações` is also what the app itself renders (`nav.settings` in

finance copy and the lexicon rows above would never catch it.

The brand takes masculine agreement: **o Vaulto**, never *a Vaulto*.

**How this is enforced (so it stops drifting):**

- `scripts/translate.mjs` names the variant in `LANG_FULL` (`Brazilian Portuguese
  (pt-BR)`) and appends the full contract above from `LOCALE_NOTES.pt` to both the
  page-JSON and blog prompts. Fixing only the JSON does not hold — the next
  `--force` re-translation overwrites it, which is how the ARY-431 register fix
  was lost. This is also why ARY-4507 inverted the prompt in the same commit as
  the copy: a rewritten page with a stale prompt is a page that re-rots.
- `npm run check:register` (`scripts/check-locale-register.mjs`) sweeps every `pt`
  surface and fails on European lexicon or `tu`-form address. It runs in
  `prebuild`, so a drifted translation cannot reach a build. It is deny-by-default:
  a genuinely correct exception goes in that script's `ALLOW` list with a reason.
  Three things make it hard to fake green, all added by ARY-4507 after each one
  was demonstrated to fail:
  - **Every rule carries a `probe` it must match**, asserted on each run. A rule
    broken by an edit is reported as dead (exit **2**) instead of silently
    matching nothing — a sweep whose rules cannot fire returns zero findings,
    which reads exactly like clean.
  - **Each corpus is asserted non-empty separately.** There are two (page JSON
    and blog Markdown) and both are found by walking directories. Losing only the
    blog half leaves 10 page surfaces and used to report a pass; it now exits 2.
  - **Exit codes are distinct:** `0` swept clean · `1` ran and found European
    copy · `2` could not run. Never collapse 2 into 0.
  - Patterns are **accent-exact** on purpose. Widening `estás` to `est[áa]s`
    makes it match the ordinary demonstrative `estas` ("estas coisas"), which is
    correct Portuguese — a guard that cries wolf is a guard someone deletes.
- Adding a variant/register contract for another locale: add a `LOCALE_NOTES`
  entry plus rules in the check script, and document the lexicon here.

## The vault noun — all 15 locales (ruling ARY-1389, lexicon ARY-1398/ARY-4258)

**Non-English copy uses the app's own vault noun. Never the English word, never a
transliteration of it, never a locally-nicer synonym.** The authority is `nav.vault`
in Asset-Vault `lib/i18n/src/translations.ts` — not this repo, and not what reads
best in isolation. A CTA saying "Start your Vault" that lands on a screen labelled
*Tresor* breaks the seam exactly where we are asking a family to trust us, so
internal consistency is the wrong test; agreement with the product is the right one.

| | es | fr | pt | de | it | nl | zh | ja | ar | hi | ru | pl | tr | ko | sv |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| **use** | Bóveda | Coffre | Cofre | Tresor | Caveau | Kluis | 保险库 | 保管庫 | الخزنة | तिजोरी | Хранилище | Sejf | Kasa | 보관함 | Valv |
| **retired** | baúl, caja fuerte | coffre-fort | caixa-forte | Schließfach | Cassaforte | — | 金库 | 金庫, ボールト | — | वॉल्ट | Сейф | skarbiec | — | 금고 | kassaskåp |

Two things that are easy to get wrong:

- **`hi` is तिजोरी, not वॉल्ट.** वॉल्ट is the English word in Devanagari — the
  un-localized form this ruling exists to kill — so `hi` is the one locale where the
  majority spelling in the corpus was the wrong one (ARY-1398 overrode value-count
  dominance 13:46 for exactly this reason).
- **Feature names are not carved out.** `/features` "Document vault" uses the same
  English common noun as the product's own container, and its body says documents are
  *"attached to the assets they belong to"* — there is no second container to name.
  So it takes the locale noun too (`Coffre de documents`, `문서 보관함`,
  `Хранилище для документов`). A carve-out would advertise a product we do not ship.

**Agreement moves with the noun** — this is why the swap is never a blind
find-and-replace. `ru` goes masculine→**neuter** (`свой сейф` → `своё хранилище`,
`изолирован` → `изолировано`); `ko` 금고 is vowel-final and 보관함 consonant-final, so
every particle shifts (`는`→`은`, `를`→`을`, `와`→`과`, while `에`/`의` are invariant);
`hi` flips gender; `pl` declines by case. Derive the new string from the existing
bytes and assert the occurrence count, rather than retyping the sentence.

**Enforcement:** `npm run guard:vaultnoun` → `scripts/check-vault-noun.mjs`, with
`guard:vaultnoun:test` as its controls; both are wired into `prebuild`. The gate
**derives its own scope** — it checks whichever `en.json` fields carry the English
noun today, so a new page is covered without editing the gate. That is deliberate:
this ruling was re-discovered on four separate surfaces (ARY-1481 → ARY-2587
`/security` → ARY-1516 trust band → ARY-4258) because a gate pinned to a hand-written
key list only ever proves the ruling holds where someone already looked. A denylist
check runs alongside it over every byte, and an unknown locale fails closed.

## Adding a NEW locale

Add the code to `LOCALES` (+ `LOCALE_NAMES`, `HREFLANG`, and `RTL_LOCALES` if
right-to-left) in `src/config/i18n.ts`, run the script, build. No per-page or
routing edits — the dynamic routes and `PAGE_LOCALES` derive from the config.

## The moving parts

| Concern | Owner file | What it does |
|---|---|---|
| Locales + hreflang correctness | `src/config/i18n.ts` | Declares the Phase-1 locales, BCP-47 hreflang codes, and **`PAGE_LOCALES`** — the per-path list of locales that actually have a live page. hreflang/sitemap only ever link locales listed here. |
| Routing | `astro.config.mjs` | Astro `i18n` config. `prefixDefaultLocale: false` keeps English URLs clean (`/security/`, not `/en/security/`). |
| Localized sitemap | `astro.config.mjs` (`@astrojs/sitemap` `i18n`) | Emits `xhtml:link rel="alternate"` pairs per page across its built locales. |
| Per-page/per-locale `<title>`, meta, canonical, OG, hreflang | `src/layouts/Base.astro` → `src/components/Seo.astro` | One `<Seo/>` per page. Pass `locale`, `title`, `description`, `path`. |
| Structured data (JSON-LD) | `src/config/structured-data.ts` + `Seo.astro` | Organization + WebSite site-wide; SoftwareApplication auto on home; `faq` / `breadcrumbs` props opt pages into FAQPage / BreadcrumbList; BlogPosting on articles. |
| UI chrome strings | `src/i18n/ui.ts` | `useTranslations(locale)` → `t(key)`, English-fallback. Nav, CTAs, footer. |

## Why `PAGE_LOCALES` is the keystone (the #1 multilingual-SEO rule)

Per ARY-399 §2e, **hreflang/sitemap must only point at pages that exist.** A
`hreflang="es"` link to a `/es/...` URL that 404s is the single most common
multilingual SEO bug. `PAGE_LOCALES` lists, per path, the locales whose page is
actually published. Until a translation lands, a page stays English-only and
emits a clean `en` + `x-default` — never a broken alternate. Verified
end-to-end: adding an `es` page makes `/` and `/es/` cross-link bidirectionally
in both `<head>` and the sitemap; removing it reverts to `en` + `x-default`.

## Translation tooling

`src/i18n/ui.ts` overlays are `Partial` per locale with English fallback, so a
half-translated locale never ships blanks. `untranslatedKeys(locale)` lists what
still needs translating (CI/QA hook). Drafting tool decision (DeepL Pro vs MT) is
the CEO/board budget call in ARY-399 §5 — the pipeline is tool-agnostic.
